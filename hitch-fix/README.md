# Hitch Fix

A performance patch for galaxy321's Lumberjack save. It removes three periodic frame freezes and one steady cost. It does not edit any other mod's files. It catches the handlers as they register, by file name, the same way Chunk Load Sieve does.

| What | Before | After |
|---|---|---|
| [AmmoMaker](https://steamcommunity.com/sharedfiles/filedetails/?id=2788256295) casing clean-up (`server/ammomaker_itemCleanUp.lua`) | 24 to 37 ms in one frame every 10 in-game minutes. The list grows forever, because an entry whose casing was picked up is never removed. | 200 entries per tick. Each entry string is parsed once. Entries with nothing left to clean are dropped. |
| Vanilla farming `SFarmingSystem:checkPlant` | About 30 ms in one frame every 10 in-game minutes, on the same frame as AmmoMaker. | 20 plants per tick. The checks are unchanged and run in the same order. A pass still running is finished before the next one starts. |
| Tuna [gun racks](https://steamcommunity.com/sharedfiles/filedetails/?id=3784677588) and [equipment racks](https://steamcommunity.com/sharedfiles/filedetails/?id=3793403177) `OnTick` sweeps | About 11 ms/s, in 2 to 3 ms bursts twice a second, even with no rack near. | Their handlers run only within 9 squares of a known rack. Chunk Load Sieve 1.2 notes rack squares as chunks load. Racks are also picked up when one is placed (`OnObjectAdded`), and a slow rescan runs one row per tick. |
| [Night Vision Framework](https://steamcommunity.com/sharedfiles/filedetails/?id=3684087856) goggle check (`NV.Shared.IsNVTaggedItem`) | About 4.7 ms/s. Every 30 player updates it tests every worn item for being goggles, about 1.8 ms each time with a full outfit, even with no goggles. | The answer is remembered per item type, so a check is one lookup per worn item. It is forgotten whenever a mod registers a new goggle type. Expected, not yet profiled: close to 0 ms/s. (1.1) |
| [This Is Your Life](https://steamcommunity.com/sharedfiles/filedetails/?id=3773911887) journal (`ThisIsYourLife/TIYLSurvivorJournal.lua`) | About 4.1 ms/s (41 µs a tick). One of its three `OnTick` handlers looks through your whole inventory every tick for a newly crafted journal that isn't tagged yet. | That one handler runs at most once a second (`JOURNAL_MS`), so a new journal is adopted within a second. The other two run every tick as before. If the file adds a different number of tick handlers, nothing is throttled. Expected, not yet profiled: close to 0 ms/s. (1.3) |
| [Better Building Plus](https://steamcommunity.com/sharedfiles/filedetails/?id=3812970899) scaffold tick (`BetterBuildingPlus/networking/server.lua`) | About 7.5 ms/s (70 to 90 µs a tick) in singleplayer. Its `OnTick` calls `require("BetterBuildingPlus/Scaffold").tick()` every tick. `Scaffold.tick` only acts once a second, so the cost is most likely the game's `require` lookup, but that part is inferred. | The handler runs at most every 250 ms (`BBP_TICK_MS`). Scaffold teardown still runs about once a second, at most 250 ms later than before. Expected, not yet profiled: about 0.3 ms/s. (1.4) |

It also carries a probe (1.5), which changes nothing. [LG Extended Electricity](https://steamcommunity.com/sharedfiles/filedetails/?id=3779562002)'s `OnTick` took about 350 ms on each of four ticks right after the save loaded (about 1.4 s of freeze, once per load). For the first 2 minutes of play the probe times that handler and its sweep (`LGEE.rebuild`, with the per-tick budget it was given), and prints `[HitchFix] LGEE probe: tick N ms, sweep N ms (budget N), rest N ms` for each tick over 30 ms. Then it puts `LGEE.rebuild` back and prints a `LGEE probe done` line. The next run shows which part is slow, before anything is patched.

A second probe (1.6) looks at Exact Minute Clock's `ISCharacterScreen:render` line, which cost about 58 ms/s in the test save with the character window closed. For the first 2 minutes it counts which panels it is drawn for and prints, every 10 s, `[HitchFix] character screen probe: N draws in 10 s` and one line per panel with its type, whether it and its parent are visible, and its size. It changes nothing.

1.7 tried to cap LG Extended Electricity's sweep budget for the first 2 minutes. It made no difference in game: each slow tick still took about 345 ms at a budget of 100, 2 or 1, so the time is spent after the budgeted walk. 1.8 removes the cap and adds stage timing to the 1.5 probe. For the probe's 2 minutes it answers LGEE's own Debug option as on (only that option), so LGEE times its stages, and each slow tick's line ends with `; stages: walk N, setRelays N, publish N, fuel line N, broadcast N, outside them N ms; relays N -> N; another sweep pending: yes/no`. LGEE also prints its own power-decision lines during those 2 minutes. That says which step to fix. Diagnostic only; nothing about LGEE's behaviour changes.

1.8's in-game run showed all of each freeze is the walk stage (walk 351 ms, everything else about 1 ms), four times in a row with relays unchanged. Reading LGEE's code, the unmetered part of the walk is `walkPlayerStructures`, which asks the game's room regions for every square of player-built structures near each generator and runs whole once per lap. 1.9 (part 10) remembers those answers for the first minute after a load: the same question asked again within 5 s gets the same squares replayed from memory, and anything built or removed (`OnObjectAdded`, `OnObjectAboutToBeRemoved`, `OnTileRemoved`) clears the memory at once. LGEE still visits every square with its own code; only the repeat lookups are skipped. After the minute the original is put back and one line reports how many walks were asked of the game and how many came from memory. Expected, not yet measured: the first lap stays ~350 ms, laps 2 to 4 become cheap.

1.9's run showed those structure walks are only about 8 ms in all (4 asked of the game, 7 answered from memory), and the four ~360 ms walk ticks stayed. So 1.10 turns part 10 off by default and adds part 11: for the probe's 2 minutes it wraps the global LGEE functions that LGEE's walk calls (43 of them, from its source: plan building, disc and stack cover, relay bookkeeping, the relay diff and so on). Inside the walk stage each outermost call is counted and timed (every call up to 200 per tick, then every 16th, scaled up), and each slow tick's line ends with `; walk steps (N ms): fnA N ms (N calls), ...; in no LGEE function N ms; first-last call ms: fnA 0-15, fnB 35-335, ...`. The costliest functions say where the time is. "In no LGEE function" is the walk's own local code and its direct calls into the game. The first and last call times show which part of the walk (buildings, structures, cord runs, machine circles, relay diff) the time falls in. Diagnostic only; nothing about LGEE's behaviour changes, and the originals are put back after 2 minutes.

1.10's run found it: each of the four slow ticks is a single `LGEE.discRegistrations` call of 340 to 406 ms, and everything else in the walk is under 5 ms. Under LGEE's takeover each running machine lights a circle. LGEE usually reuses a pre-worked shape for it, but when another generator stands on one of that shape's squares it works that circle out square by square (`LGEE.cover`). It keeps the answer, but throws it away whenever a generator is filed or removed anywhere, which happens on each of the first laps while chunks stream in. So the same circle is worked out four times. 1.11 (part 12) wraps `LGEE.discRegistrations`. For a cover, it first asks LGEE's own `canHost` (passed in with the call) about every square the answer can depend on: about 2,000 cheap lookups for a 20-tile circle. If every answer matches the last time the same circle was worked out, it hands back a copy of that answer; otherwise it calls the original. The result is always what LGEE would have worked out. Expected, not yet measured: one ~350 ms freeze after a load instead of four. The probe line adds `; circle covers: N worked out (N ms), N re-used (N ms checking)`, and `LGEE circle covers so far: ...` is printed 2 minutes after start.

1.11's run never re-used a cover: each of the four passes saw different answers, so each was worked out again (4 worked out, 1,572 ms). The likeliest cause is that generators near the base are filed one by one as their chunks stream in, and each new one changes what `canHost` answers inside the circle; that is inferred, not shown. 1.12 does three things. Each circle keeps up to 8 answers, one per set of `canHost` answers seen. A cover that has to be worked out says why on the probe line, either `not seen before` or which squares changed (for example `2 changed (10412,9873=false new)`), and the 2-minute summary lists the reasons. And the answers are kept on disk in `Zomboid\Lua\HitchFix_LGEE_circles.txt` as plain numbers, which LGEE's own `relayKey` and `chunkKey` turn back into registrations, so the next load, which streams the same chunks in roughly the same order, can find them. The file is ignored if LGEE's cover gives a different answer on a small fixed test than when the file was written, for example after an LGEE update. Any match is still exact. Expected: the first load after installing still has the freezes; later loads should not, if their passes see the same answers. Delete the file to start afresh.

1.13 fixes three things found in a code review; nothing else changes. If a mod takes one of the caught handlers off its event (Tuna's rack handlers, AmmoMaker's casing clean-up), Hitch Fix stops running it too; before, it kept calling it, and a re-add ran it twice. Neither Tuna rack mod removes its handler in its current version, so this was latent. The first rack rescan now runs as the game starts instead of 10 s in, so without Chunk Load Sieve a rack right beside you at load is serviced from the first second. And the night-vision answers are forgotten every 10 s (`NV_FORGET_MS`), so a goggle type registered by some other route than the framework's own function is picked up within 10 s; the cost is one full check per worn item type every 10 s.

## Install

- Copy `HitchFix` to `Zomboid\mods\` and enable it.
- Update Chunk Load Sieve to 1.2, which adds `ChunkLoadSieve.watch`. Without 1.2, racks are found only by the rescan, which runs every 10 s.
- Load order does not matter. The file name `!!!_HitchFix.lua` sorts before the patched mods' files.

## Check it is working

The console shows:
- `[HitchFix] caught ...` for each handler it caught.
- `[HitchFix] active (1.13), caught: ...` (ending in `LGEE circle covers re-used (N from file), LGEE stage timing, LGEE walk steps (N functions)` when LG Extended Electricity is on), `[HitchFix] farming checks spread over ticks` and `[HitchFix] night vision goggle check remembered per item type` when the game starts.
- Every 10 real minutes, a line with the casing, farming, rack and night-vision item type counts.

## Turn parts off

Set `ENABLE_AMMO`, `ENABLE_FARMING`, `ENABLE_RACKS`, `ENABLE_NV`, `ENABLE_TIYL_JOURNAL`, `ENABLE_BBP_TICK`, `ENABLE_LGEE_PROBE`, `ENABLE_LGEE_STAGES`, `ENABLE_LGEE_REGION_CACHE` (off by default from 1.10), `ENABLE_LGEE_WALK_STEPS`, `ENABLE_LGEE_DISC_CACHE`, `ENABLE_LGEE_DISC_FILE` or `ENABLE_CHARSCREEN_PROBE` at the top of the Lua file to `false`.

1.2 also throttled Take A Bath And Shower's grime moodle. That moved to UI Throttle 1.1, so update both together.

## Test

Run `python3 mock_test.py` (needs `lupa`). It runs the patch against stand-ins for the real files, with and without Chunk Load Sieve.
